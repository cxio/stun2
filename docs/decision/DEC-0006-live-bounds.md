# DEC-0006 粗测/精测可携带区间

## 背景 （Context）

构想写明：粗测与精测是两个独立探测周期（均从预探测创建映射开始），不必在同一服务器上进行；精测输入为粗测的最后成功间隔 `n` 与最后失败间隔 `M`，无 `M` 则不能精测。DEC-0001 已定：一次调用绑定一台服务器与一个地址族、库不把粗测进度持久化、跨服务器由应用综合。

未定的是应用跨调用到底持有什么、第二次调用往哪填。没有这份决策，Spec 无法写出与可分离性一致的公开 API：只返回成功间隔会丢掉 `M`；只用起始间隔会变成再跑一遍粗测。

## 决策 （Decision）

1. **可携带区间。** 粗测（以及随后的精测过程）导出一对时长：最后一次成功、最后一次失败。它描述的是本端 NAT 映射行为，不含服务器身份。换服务器由应用换连接材料；库不校验区间来自哪一台服务器。
2. **导出给应用，库不记住。** 一次调用结束时必须把当前区间交给调用方。应用跨调用、跨服务器持有。DEC-0001「不持久化」指库不写盘、不跨进程、不在库内保存上次调用的区间；把区间放进返回值不是持久化。
3. **精测只认区间。** 只精测时必填可携带区间。起始间隔不是 `n` / `M` 的替代；只精测时忽略起始间隔与粗测迭代上限。
4. **无失败间隔则不能精测。** 最后失败未出现，或未严格大于最后成功，不能进入精测。粗测一直成功直到 40 分钟上限或次数上限，属未收敛，不进入精测。
5. **一次调用三种模式。** 一次状态机构造 / Runner 绑定一台服务器、一个地址族，只能是：只粗测；只精测；同机先粗后精。同机先粗后精时，精测仍从预探测新开一轮（粗测结束时旧映射已失效）。
6. **构造与 Runner 同一配置。** 区间已提供则算法从精测起，I/O 仍从预探测起。从粗测起的调用，起始间隔仍必填、无默认值。

## 理由 （Rationale）

可分离性是构想的明示能力，不是可选优化。区间是本端 NAT 的属性，与「客户端主导节奏、服务器只按请求响应」一致，换节点不必重测粗区间。

若结果只有成功间隔，应用无法启动精测。若允许用起始间隔顶替，第二次调用的语义变成粗测，代价和含义都不同。把区间做成值对象交给应用，既落实可分离性，又不把跨调用状态拉回库内。

## 影响 （Consequences）

- Spec 必须在探测结果中带出区间、在配置中注入区间，并规定与 Runner 共用该配置的构造入口。
- 区间类型与「可否精测」判断落在根包 `stun2`；步进纯函数以该区间为输入。`stun2/client` 的配置与结果引用之。
- 从粗测起的调用仍必填起始间隔；只精测时必填的是区间，不要求起始间隔。
- 应用自行判断持有的区间是否仍适用于当前网络；库不因换服务器拒绝区间。

## 构想层依据 （Conception References）

- `conception/keepalive.md`：可分离性；精测以粗测的 `n` / `M` 为输入；无收敛目标则不能精测；起始间隔与精测精度可配置；客户端主导节奏。
- `DEC-0001`：状态机 + Runner；一次调用一个地址族；库不持久化粗测进度；跨服务器综合由应用做；从粗测起起始间隔必填。
