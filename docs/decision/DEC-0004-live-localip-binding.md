# 0004 — STUN:Live 会话标识中 LocalIP 的取值来源与服务端绑定建议

## 背景

`keepalive.md` 会话标识（SN）构造中，服务端一侧的 `LocalIP` 原文仅说明"服务器 IP。客户端已知服务器 IP，可执行验证"（`keepalive.md:96-97`），未定义服务端存在多个网络接口/多个公网 IP（IPv4/IPv6 双栈、多归属主机）时，应该使用哪一个具体 IP 值。若不同实现在此处理解不一致（例如误用配置层面的"规范"服务器身份地址，而非实际提供服务的那个连接地址），会导致客户端 HMAC 验证失败、误判 NAT 映射已失效。

此外，标准 `net.UDPConn` 绑定通配地址（`0.0.0.0` / `::`）时，应用层既无法确定某个入站包的具体目的 IP，发包时源 IP 也由内核路由表决定、无法精确控制，这是本问题在工程实现上的直接根源。

## 决策

1. **协议层 MUST**：服务端构造 SN 时使用的 `LocalIP` **MUST** 等于客户端本次实际拨号连接所使用的那个具体服务 IP（即该 QUIC 连接的服务端地址），**而非** 任何配置层面声明的"规范"服务器身份地址。
2. **实现建议 SHOULD**：服务端 **SHOULD** 按每一个对外提供服务的公网 IP 分别绑定独立的 `net.UDPConn`（及对应的 `quic.Transport` 实例），而非绑定通配地址；如有多个服务 IP（例如 IPv4 + IPv6 双栈，或多个公网出口），相应绑定多个 socket。这样可以保证服务端在发送 SN 时能够准确知道并控制所使用的源 IP。

## 理由

- 按具体 IP 分别绑定 socket 是多归属 UDP/QUIC 服务端的常见工程实践，传统 STUN/TURN 服务器实现中也普遍采用类似做法，以避免通配监听下"源/目的 IP 不确定"的问题，并非临时权宜之计。
- 若确有场景无法枚举所有本地 IP（如容器化环境、动态 IP 分配），仍可通过带外控制信息（如 `IP_PKTINFO`）在通配 socket 上获知/指定具体 IP，但这属于更高复杂度的备选实现路径，本决策不强制，仅推荐默认做法。
- 该建议只影响服务端内部实现方式，不改变 SN 的 wire 格式或验证语义，因此标记为 **SHOULD** 而非 **MUST**，留给具体 `stun2p` 实现按自身部署环境选择。

## 影响范围

- **Conception**：`keepalive.md`"会话标识"节、"服务端操作"节。
- **协议层影响**：`LocalIP` 取值语义是协议层规则（两个实现若理解不一致会导致验证失败）；具体绑定方式是实现建议，不影响协议互通。
