# 0005 — NewHost 受托 Notice 消息格式

## 背景

`conelevel.md`"受托服务器"节描述了委托服务器向受托服务器传递的必要信息（`Notice`）：`Version`、客户端公网映射地址、客户端会话密钥封装 `SHA256(Key32)`。此前该消息格式未纳入协议层规范，`DEC-0001` §「PoW / Equi-X / 反滥用」中也仅以"如需标准化受托 Notice 消息格式以便不同 stun2p 实现互通，可将 Notice 基础字段格式放入协议层"这种条件句搁置了问题。

考虑到委托 `NewHost` 探测是 P2P 网络中跨节点协作的核心场景之一，不同 `stun2p` 实现之间若要互相委托，Notice 格式不统一将导致协作完全失败，因此本决策正式将其纳入协议层。

## 决策

**Notice 消息字段格式（协议层 MUST）**：

| 字段 | 长度 | 说明 |
|------|------|------|
| `Version` | 1 字节 | 版本号，初始值 `1` |
| `ClientAddr` | 定长（`WireAddr`） | 客户端公网映射地址（`IP:Port`） |
| `KeyDigest` | 32 字节 | 客户端会话密钥封装 `SHA256(Key32)`（**不** 传递原始 `Key32`） |
| `AppIDLen` | 1 字节（`uint8`） | `0` 表示未提供 `AppID` |
| `AppID` | `AppIDLen` 字节，UTF-8 | 应用实现自身标识（可选），**MUST** ≤ 64 字节 |
| `AppDataLen` | 2 字节（`uint16`，大端） | `0` 表示未提供 `AppData` |
| `AppData` | `AppDataLen` 字节，不透明 | 应用自身额外数据（可选），**MUST** ≤ 1024 字节 |

**行为规则（协议层 MUST）**：

1. 受托服务器 **MUST** 将 `AppID` 与 `AppData` 视为不透明扩展数据；**MUST NOT** 仅因无法识别 `AppID` 或不理解 `AppData` 内容而拒绝该 `Notice`——只有固定字段（`Version`/`ClientAddr`/`KeyDigest`）解析失败时才可拒绝。
2. 委托方在未使用 `AppID`/`AppData` 时，**MUST** 将对应的长度字段填 `0`（而非省略字段本身），保持消息结构定长可解析。
3. `Notice` 消息在委托服务器与受托服务器之间的安全连接（通常为 QUIC）上传输，**不** 出现在面向客户端的裸 UDP 探测面。

## 理由

- 统一的是 **容器格式**（能否正确解析、能否安全跳过/透传未知内容），而不是字段内容的具体语义——`AppID`/`AppData` 的实际含义仍由各应用生态（`stun2p` 及其上层）自行约定，符合 `DEC-0001` 的分层判定标准。
- 用长度前缀而非固定枚举 ID 来标识 `AppID`，是因为目前不存在一个中心化的注册机构来分配数值 ID，自由格式字符串更适合去中心化的多实现场景。
- 上限（64 字节 / 1024 字节）用于避免服务器间协作通道被滥用来传递过大数据，同时留出足够空间满足常见的应用标识与少量扩展数据需求。

## 影响范围

- **Conception**：`conelevel.md`"受托服务器"节（`Version`/客户端地址/密钥封装 + 新增 `应用标识`/`应用数据` 字段）。
- **下游 Proposal**：`wire-spec-v1.md` 待决问题 W3（"受托 Notice 是否升格为协议层 wire 格式"）由本决策正式回答：**是**，并给出具体字段表，后续重写 Proposal 时应据此补充 Notice 的编解码规范。
