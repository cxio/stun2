# 0003 — STUN:Cone 关闭握手、服务端等待超时与资源释放

## 背景

`conelevel.md` 原文（Step.2）仅说明"服务端收到信息后，即可通知客户端关闭 QUIC 连接，回退到……UDP 连接上通讯"，未定义服务端何时真正开始发送探测 SN。如果服务端在通知发出后立即发包，客户端可能尚未完成"关闭 QUIC → 切换到 `ReadNonQUICPacket` 读取"的状态切换，导致探测包（尤其是三次冗余中的首个包）在客户端 demux 就绪之前抵达并丢失。

Conception 现已修订为"在服务器通知客户端关闭 QUIC 连接，并收到客户端的关闭确认后"才执行 `NewPort`/`NewHost`（`conelevel.md:118`），但"关闭确认"的具体机制、服务端等待多久、等不到怎么办，仍需要明确规定。

## 决策

1. **协议层 MUST**：服务端在发送任何探测 SN 之前，**MUST** 先感知到客户端一侧的 QUIC 连接已经实际关闭——通过 **QUIC 传输层自身的连接关闭事件**（即客户端主动关闭连接后服务端观测到的对端连接状态转换，例如收到对端下发的关闭信号或连接对象进入已关闭状态）来判定，**不** 引入额外的应用层"确认"消息。即"关闭确认"= 服务端通过 QUIC 协议栈本身观测到客户端已关闭连接，而非一条独立的业务消息。
2. **协议层 MUST**：服务端 **MUST** 维护一个 **独立于 QUIC 连接空闲超时（`MaxIdleTimeout`）配置** 的显式等待定时器，默认 **5 秒**（与客户端默认等待窗口对齐）。定时器到期后如果仍未观测到客户端关闭 QUIC 连接的事件，服务端 **MUST** 无条件释放该 `STUN:Cone` transaction 的状态，且 **MUST NOT** 再发送任何探测 SN。
   - 之所以要求"独立于 QUIC 空闲超时"：客户端优雅关闭（正常调用关闭）时，服务端能很快收到关闭信号；但客户端异常消失（进程崩溃、网络中断）时，服务端只能依赖 QUIC 自身的空闲超时机制感知连接已死——而该机制的默认配置通常远大于本决策要求的等待时长。如果服务端的等待定时器直接绑定/依赖 QUIC 空闲超时配置，会导致资源占用时间被动大幅拉长，形成低成本的资源占用风险。因此服务端必须用自己独立维护的定时器兜底，到点即放弃，与 QUIC 连接对象此时的实际状态无关。
3. **应用层**：客户端自身等待探测 SN 的超时窗口（**5 秒**，从客户端 **发起关闭** 自身 QUIC 连接的那一刻起算）为推荐默认值，客户端 **MAY** 按自身网络状况配置为其他值，不强制。
4. **协议层 MUST**：服务端在该 transaction 进入完成状态（两路径探测发送完毕，或等待窗口结束）后，**MUST** 主动关闭与该客户端之间的 QUIC 连接（如尚未关闭），以统一资源清理行为，不依赖客户端单方面关闭连接。

## 理由

- 用"观测 QUIC 自身关闭事件"而非"额外的应用层 ack 消息"作为握手确认，避免了在已经很紧凑的探测时序（累计探测仅 0.5~1.1 秒）中再插入一次消息往返，且天然利用 QUIC 协议栈已有的可靠信令能力。
- 引入独立于 QUIC 空闲超时的等待定时器，是为了防止"客户端异常消失、迟迟不触发 QUIC 层面的关闭信号"这一场景下服务端资源被无限期占用——这也堵住了"开大量连接发起 Cone 请求后不管"这种低成本占用服务端资源的路径。
- 服务端在 `Done` 后主动关闭 QUIC 连接，统一了资源回收的责任方（不依赖客户端配合），简化了服务端实现，也避免不同实现在这一点上出现清理时机不一致的问题。

## 影响范围

- **Conception**：`conelevel.md` Step.2（服务器）、"客户端超时"节。
- **下游 Proposal**：`transaction-spec-v1.md` §2.3 中原有的 `T_probe_start`"三条规则取最晚"（50ms/200ms 猜测性时序）应整体替换为本决策的"等待 QUIC 关闭事件"模型；待决问题 T2（"Cone 服务端是否 MUST 在 Done 后主动 Close QUIC"）由本决策正式回答：**是**。

## 附注（T3）：`PreAckQueue` 机制已废止

`transaction-spec-v1.md` §2.4 原先设计了 `PreAckQueue`（暂存 `CONE_ACK` 到达之前收到的 UDP 载荷，供 ACK 后补验证），用于应对"服务端过早发包"的竞态。

本决策生效后该机制已无存在必要：服务端在观测到客户端关闭 QUIC 连接之前 **MUST NOT** 发送任何探测 SN，而客户端关闭 QUIC 连接这一动作本身发生在客户端收到 `CONE_ACK` **之后**（见状态机 `AwaitingAck → ProbeWait`）。因此任何合法探测 SN 在时间上只可能出现在客户端已进入 `ProbeWait` 之后，不存在"ACK 前收到合法探测包"的场景。`ProbeWait` 之前（`DemuxReady`/`AwaitingAck` 阶段）收到的任何裸 UDP 载荷均非本 transaction 的合法探测包，**MUST** 直接丢弃，无需队列暂存。

重写 Proposal 时应删除 `PreAckQueue` 相关状态、字段与测试用例。
