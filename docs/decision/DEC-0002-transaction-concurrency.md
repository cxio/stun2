# 0002 — STUN:Cone / STUN:Live Transaction 并发规则

## 背景

`STUN:Cone` 与 `STUN:Live` 的会话标识（SN）均为 `Rnd16(16) + HMAC(32) + TmpN(464~1024)` 结构，仅首字节部分位（`Rnd16[0]` 高 2 位、Cone 的 `from` 位）携带极少量语义，**不含任何 transaction 标识或来源地址信息**（`conelevel.md:110-111`：SN 构造中没有服务端地址，因为对客户端来说受托服务器未知，无法验证）。

如果同一个 `net.UDPConn` 上同时存在多个未完成的 Cone/Live transaction（各自持有不同的 `Key32`），客户端收到一枚裸 UDP SN 包时，无法仅凭包内容或来源地址确定它属于哪个 transaction：

- `NewPort` 子路径：源 IP 固定等于对应服务器的已知 IP，理论上可用远端 IP 辅助区分。
- `NewHost` 子路径：源 IP **按设计对客户端不可预知**（可能是源服务器的另一个 IP，也可能是完全陌生的受托服务器 IP，这正是 `Exclist` 存在的原因），**不能**用远端 IP 判定归属。

因此"按远端 IP 区分并发 transaction"的方案对 `NewHost` 天然不成立，只要允许同一 `UDPConn` 上并发多个 transaction，就必然引入路由歧义（只能退化为遍历所有活跃 `Key32` 逐一尝试 HMAC 验证）。

## 决策

1. **协议层 MUST**：同一 `net.UDPConn` 上，任意时刻 **最多只能有一个** 处于探测等待状态的 `STUN:Cone` transaction（从客户端关闭 QUIC 连接进入裸 UDP 探测阶段，到收到有效 SN / 等待窗口结束为止）。
2. **协议层 MUST**：同一 `net.UDPConn`（对应同一个 `Port.0` 映射）上，任意时刻 **最多只能有一个** 未完成的 `STUN:Live` transaction。
3. **应用层**：客户端是否要同时对多个服务节点发起 Cone 或 Live 探测以提升效率/可靠性，属于应用层调度策略（不影响协议消息的解析与验证）；若选择并发，客户端 **MUST** 为每一个并发 transaction 各自创建独立的 `net.UDPConn`，规则 1、2 在每个 `UDPConn` 内部仍然适用。
4. **协议层 MUST NOT**：任何实现 **MUST NOT** 依赖"远端 IP"作为区分并发 transaction 的手段——原因见上文背景，`NewHost` 的源 IP 对客户端不可预知，此假设不成立。
5. **不纳入协议常量**：服务端对同一客户端可并行处理的 `STUN:Live` transaction 数量上限，**不** 写入协议常量，由服务器实现自行配置/限流（应用层 / 服务器实现层，参见 `DEC-0001` §「超时、重试、置信度」的同类归属逻辑）。

## 理由

- 与"允许并发 + 遍历 `Key32` 验证"的备选方案相比，强制串行化的实现和互操作性验证成本都更低，且与整体设计哲学一致（`conelevel.md:173` 明确强调"考虑简单性和效率"）。
- 把"是否并发探测多个服务节点"留给应用层，符合 `DEC-0001` 的判定标准：这一选择不影响任何一次具体消息的解析或验证语义，只影响成功率、效率与成本。
- Live 服务端并发上限本质是资源管理/限流策略，两个独立实现选择不同上限不影响协议互通，因此归入应用层，与 `DEC-0001` 已有归类（超时/重试/置信度类）保持一致，不额外固化为协议常量。

## 影响范围

- **Conception**：`conelevel.md`"正式探测（STUN:Cone）"节、"会话标识"节；`keepalive.md`"探测循环"节。
- **下游 Proposal**：`transaction-spec-v1.md` §1.1 已有的"客户端 MUST NOT 并发两个未完成的 Cone/Live transaction"表述与本决策一致，现由本 Decision 正式背书；§3.7"每客户端 ≤4 并发 LiveTx"的具体数字建议应改写为"由服务器实现自行决定，不作为协议 SHOULD 默认值"。

## 备选方案（已否决）

- **允许同一 `UDPConn` 上并发多个 transaction，收到 SN 后遍历所有活跃 `Key32` 尝试 HMAC 验证**：被否决。理由：增加了客户端实现复杂度和验证开销，且与"简单性优先"的设计取舍不一致；在多数场景下，应用层完全可以通过多开 `UDPConn` 达到同样的并发效果，没有必要在协议层引入按 Key 遍历的复杂度。
