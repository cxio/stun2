# 0006 — STUN:Cone Exclist 容量上限固定为 256，不做协商

## 背景

`conelevel.md`"客户端 Step.1"节提到 `Exclist`（排除清单）用于避免 `NewHost` 选中客户端近期已联系过的 IP，并说明"如果客户端提交过大的 Exclist，服务器可能拒绝为其服务"，但未给出具体的数量上限或协商机制。`wire-spec-v1.md` 此前已自行给出 `MaxExclistEntries = 256` 的具体数值（§4.2、§8），但未有对应 Decision 支撑；其待决问题 W2 也提出"`MaxExclistEntries` 是否需可协商"尚未有定论。

## 决策

1. **协议层 MUST**：`Exclist` 条目数量上限 **固定为 256**，**不** 提供版本协商或动态调整机制。服务端收到超过此上限的 `Exclist` **MUST** 拒绝该 `STUN:Cone` 请求（返回对应错误状态，如 `EXCLIST_TOO_LARGE`）。
2. **应用层建议**：客户端应当遵循 `conelevel.md` 已有的"良好实践"，在初始上线后即尽快请求 `STUN:Cone` 探测服务——此时 `Exclist` 处于空或接近空的状态，天然不会触及上限。256 条对典型的半小时排除时间窗口内的正常使用场景应属充裕。

## 理由

- 固定上限、不提供协商机制可以显著简化协议（无需额外的版本/能力协商往返），符合整体设计中"考虑简单性和效率"的取舍原则。
- Exclist 的"近期"时间窗口（如半小时）属于应用层维护策略（`DEC-0001` §「Exclist 维护策略」已有归类），客户端只要遵循"尽早请求探测"的良好实践，正常场景下条目数远低于 256，不会构成实际限制。
- 若未来确有需要突破该上限的场景，应作为新的协议版本变更处理，而非在 v1 引入协商复杂度。

## 影响范围

- **Conception**：`conelevel.md` 客户端 Step.1 节（`Exclist` 字段）。
- **下游 Proposal**：`wire-spec-v1.md` §4.2/§8 中 `MaxExclistEntries = 256` 的数值现由本决策正式背书，无需修改数值本身；待决问题 W2 由本决策正式回答：**不可协商，固定 256**。
