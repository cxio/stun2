# NAT映射存活期探测：`STUN:Live`

NAT 映射有存活期，通讯静默超时后 NAT 映射会失效，对某些应用来说，知道这个存活期可能很重要。

与 STUN:Cone 探测类似，客户端与服务器间的通信采用 *QUIC 安全连接 & 底层 UDP Socket 复用* 模式，其中 QUIC 用于安全传输，底层裸 UDP 用于 NAT 映射探测。


## 前提条件

- 服务端启动后创建了一个**32**字节的随机密钥 `BaseKey`，用于所有的会话验证。
- 服务端运行一个存活期探测服务 `quic.Listener`，由一个已经存在的 `net.UDPConn` 创建。


## 预探测：Step.0 创建NAT映射

客户端创建到服务器的普通 UDP 拨号连接（`net.UDPConn`），并基于此连接创建一个 QUIC 连接。这样就创建了客户端到公网的 NAT 映射。

然后客户端向服务器发送预探测请求 `STUN:Live.Port`，服务器返回：

- 客户端公网映射地址：`IP.0:Port.0`。
- 探测证明：`Validation` = Timestamp || `HMAC_SHA256(BaseKey, domainTag || IP.0 || Port.0 || Timestamp)`。

> **说明：**
> - 域标签 domainTag 简单地采用 `STUN:Live.Port` 即可。
> - 时间戳 `Timestamp` 为证明的有效截止时间，通常**10**分钟，可配置。

> **编码：**
> `Timestamp` 为 Unix 时间，单位：秒；变长整数（ULEB128 最简编码）。

客户端检查映射地址与自身本地地址是否相同（含端口），确认自己是否处于 NAT 之内。

如果客户端处于 NAT 之内，则继续下面的流程。

- 暂存获取到的自身的地址 `IP.0` 和 `Port.0`。
- 暂存服务端派发的批准证明 `Validation`。后续需要此批条证明 `Port.0` 的合法性。


## 客户端：Step.1 创建新 QUIC 连接

1. 客户端关闭之前与服务器的 QUIC 连接（仅 quic.Conn），退化到纯 UDP 链路。
2. 使用一个*新的*随机端口向同一服务节点拨号，创建一个新的 QUIC 连接（新的 Socket，正常 keep-alive）。

至此，客户端和服务器之间有了两条通讯链路：

- 裸 UDP 旧连接：用于接收服务端发送的探测消息。
- 新 QUIC 连接：用于客户端与服务器通讯：发送 `STUN:Live` 请求，让服务器在旧连接上发送探测包。

客户端关闭 QUIC 连接之后，即记录首次探测的起始时间（`Time.0`）。客户端将在初始的间隔时间后，向服务器发送 `STUN:Live` 探测请求。

> **设计：**
> 与传统探测不同，本设计中延时不由服务器控制，客户端掌控所有探测节奏。服务器简单响应即可。
> 这简化了服务器端的逻辑（无状态），也让客户端更灵活，可自由控制精度。


## 客户端：Step.2 请求服务（STUN:Live）

当预设的间隔时间到达后，客户端需要向服务器请求发送探测包。

但在此之前，为强化可靠性，避免客户端在环境迁移后做无效探测，会先执行一次「预环境验证」。


### 预环境验证

在新的 QUIC 连接上，客户端发送 `STUN:Addr` 请求。请求时间适当提前，比如**5**秒。

服务器返回响应之后，客户端提取 IP 与之前暂存的 `IP.0` 核实比对：

- **相同**：说明外部网络环境没有改变，继续执行后续流程。
- **不同**：说明外部网络环境已经改变，此次探测流程结束。如需继续，应从*Step.0*重新开始。


### 探测请求

当规定的间隔时间到达后，在新的 QUIC 连接上，客户端向服务器请求 `STUN:Live` 探测服务，数据包含：

- Version:    版本号（初始值 1）。
- Key32:      即时生成的会话密钥，32字节随机序列。**注**：每次都不同。
- Port.0:     裸 UDP 连接上的旧端口号（即之前暂存的端口号）。
- Distance:   申请的时间窗口大小。即本轮探测生存期预期时长 + 余量（如**3**分钟）。
- Validation: 之前暂存的服务端派发的批准证明。

> **注**：服务端收到请求后的操作见 [下文](#服务端)。

同时，客户端会在 `Port.0` 上侦听，收到服务端发送的探测包后验证并回应：

- 回应包负载为即时构建的 `SN`（见下文）。
- 收到一个回应一个，同时更新*探测间隔*的起始时间（`Time.0`）。

> **探测间隔：**
> 下一次 `STUN:Live` 请求和本次 `Time.0` 的时间间隔，也是 NAT 映射生存期的参考目标。

服务器会在 QUIC 连接上回复新的探测证明 `Validation`，客户端需要更新暂存的旧值。


### 附：状态判断

对于客户端在 `Port.0` 上的监听来说：

- 如果收到探测包，表示映射没有改变，原映射端口依然有效。
- 如果没有收到探测包（**12**秒超时），表示映射已经改变，探测不可达。


## 会话标识

客户端与服务器之间在纯 UDP 链路上发送的消息包为会话标识 `SN`。这是一个有着内在构造规则的字节序列。

**SN**的构造规则如下（伪代码）：

```go
// Rnd16: 16字节随机序列。
// Rnd16[0]: 首字节高两位置零，标识非 QUIC 数据包。
// 注意：
// 虽然QUIC会话会关闭，但服务端普遍监听，依然需要这一清位分辨。
Rnd16[0] &= 0x3F

// domainTag:
// - 服务器："Server@STUN:Live"
// - 客户端："Client@STUN:Live"
// LocalIP:
// - 客户端：自己的公网IP，服务端可通过UDP连接获取。
// - 服务器：服务器IP。客户端已知服务器IP，可执行验证。
// TmpN: 变长随机字节序列，用于隐藏 SN 的长度特征。长度：16 ~ 1024
// 前段固定 16 + 32 = 48 字节。
SN = Rnd16 || HMAC_SHA256(Key32, domainTag || Rnd16 || LocalIP || TmpN) || TmpN
```

**注意**：不论服务器还是客户端，每发送一个 `SN` 都必须即时构建（各自不同）。


### 附：SN 验证

```go
// SN 解构
Rnd16 := SN[:16]
TmpN  := SN[48:]
Hash  := SN[16:48]

// LocalIP:
// - 客户端：取服务器 IP 填入。
// - 服务器：取客户端公网 IP 填入。
return Hash == HMAC_SHA256(Key32, domainTag || Rnd16 || LocalIP || TmpN)
```


## 服务端

服务器监听并接收任意客户端的探测请求，根据传递来的数据：

- 验证 `Validation`。
- 根据客户端的 `Distance` 申请，更新 `Validation`（最长不超过**40**分钟）。
- 构造目标地址 `clientIP:Port.0`，发送探测包。

**验证证明&核实目标地址**：

```go
// 提取时间戳
Timestamp := Validation[0:len(Validation)-32]

// 是否有效期内：
if Now.Timestamp > Decode(Timestamp) {
    return false // 证明过期
}
// 有效载荷
Valid32 := Validation[len(Timestamp):]

// 目标是否合法：
// clientIP: 从 UDP 连接提取的远端公网 IP
// Port.0: 客户端传递过来的目标端口
Hash := HMAC_SHA256(BaseKey, domainTag || clientIP || Port.0 || Timestamp)

if Hash == Valid32 {
    return true // 端口合法
}
```

**更新探测证明：**

```go
// Distance 客户端申请窗口（≤40分钟）
Expire := Now.Timestamp + Distance
Timestamp := Encode( Expire )

// 新的有效期证明
Validation := Timestamp || HMAC_SHA256( BaseKey, domainTag || clientIP || Port.0 || Timestamp )
```

服务器将更新后的 `Validation` 发给客户端（QUIC 链路），然后在纯 UDP 链路上发送即时构造的 `SN`……直到收到客户端回应或冗余发送结束。


### 发送频率

服务器发送的消息遵循指数退避策略，初始间隔从 100ms 开始，逐次加倍直到收到回复或超时。

间隔时间（ms）：100, 200, 400, 800, 1600, 1600, 1600, 1600, 1600 结束。
累计时长（ms）：100, 300, 700, 1500, 3100, 4700, 6300, 7900, 9500 结束。


### 无状态服务

服务端依赖批准证明 `Validation` 验证客户端请求的合法性，无需存储客户端的任何信息，仅暂存 `Key32` 用于验证客户端回包（终止发送的通知），结束则丢弃。

这基本上是一种无状态的逻辑，服务端的操作十分简单：

- 收到请求，验证&构造目标地址。
- 即时创建 `SN` 并发送……每个 `SN` 都不同。
- 接收远端回应，验证并终止后续冗余发送。

服务器验证客户端回应包（`SN`）的逻辑参考上面 [§.附：SN 验证](#附sn-验证) 章节。


### 附：探测原理

前一次的 `STUN:Live` 成功交互（`Time.0`），是下一次 `STUN:Live` 交互的计时起点。两者的间隔时间即为 NAT 映射的存活期探测值。

客户端会连续尝试递增的多个间隔时间，向服务器发送 `STUN:Live` 请求，直到某次的探测包超时（NAT 映射失效）。此时前一次成功交互的*探测间隔*时间即为 NAT 映射的存活期。

```go
// Time.0: 上一次回包结束
探测间隔 := 新 STUN:Live 请求 - Time.0

// 最后一个未超时测试
LifeTime := 探测间隔
```


## 探测循环（客户端 <=> 服务器）

在一个探测周期内，客户端需多次向服务器请求 `STUN:Live`（**Step.2**）。

客户端超时设置为**12**秒，如果在 12 秒内没有收到服务器的任何探测包，即可终止该轮探测。上一次成功交互的探测间隔时间即为有效生存期。

服务端如果未收到客户端的*结束发送*回应消息，则发送完 9 次后自然结束（无超时）。


### 粗测

粗测是一个快速的探测流程，目的是快速获得一个大致的存活期值。

粗测的起始间隔是灵活的，用户应当根据自身所处环境，配置一个合适的折中值：

- **成功**：下一次间隔时间翻倍，直至探测失败。
- **失败**：回退上一次变化量（增量/减量）的一半。如果首次即失败，回退初始间隔的一半，即进入收敛期。
- **结束**：最后一次失败=>成功，或抵达上限时。结果为最后一次成功时的值。

下表伪代码示意了探测流程：

```go
// 假设起始间隔 3m
3m => 成功 =>   // 初始值
6m => 失败 =>   // 3*2 = 6
4.5m => 成功 => // 6 - (3/2) = 4.5
Done => 4.5m    // 结束
```

```go
// 假设起始间隔 2m
2m => 成功 =>   // 初始值
4m => 成功 =>   // 2*2 = 4
8m => 失败 =>   // 4*2 = 8
6m => 失败 =>   // 8 - (4/2) = 6
5m => 失败 =>   // 6 - (2/2) = 5
4.5m => 成功 => // 5 - (1/2) = 4.5
Done => 4.5m    // 结束
```

为避免不必要的收敛细分迭代（一直失败），用户可设置迭代**次数**上限：如果一直没有「失败=>成功」，则取最后一次成功的值为结果。

```go
// 迭代次数上限 5
2m => 成功 =>   // 初始值
4m => 成功 =>   // 2*2 = 4
8m => 失败 =>   // 4*2 = 8
6m => 失败 =>   // 8 - (4/2) = 6
5m => 失败 =>   // 6 - (2/2) = 5
End => 4m       // 抵达上限约束，取上面最后一次成功时的值
```

首次即失败（配置值不恰当）：

```go
// 初始间隔 5m
5m => 失败 =>   // 初始值
2.5m => 成功 => // 5 - (5/2) = 2.5
Done => 2.5m    // 结束
```

如果首次即失败，且一直失败，则可能是配置值过高，且设置了较低的迭代次数上限。用户应当修改配置。如果配置值不高且迭代次数也不低，则可判定为异常。用户可以尝试向不同的服务器节点请求服务。

从上面的示例可以看出，恰当的初始配置值可以显著优化请求次数，缩减总的探测时间。

> **注意：**
> `STUN:Live` 允许的时间窗口最长只有**40**分钟，因此探测到的存活期最长只能到此。


### 精测

粗测成功之后，如果觉得时间粒度太粗，可启动精测流程。

精测在粗测的基础上进行，对粗测中最后一次失败和成功的时间差，按二分规则增减时间探测。假设粗测的存活期为 `n`，最后一次失败时为 `M`，则待探测时长为 `D = M-n`，精测初始间隔时间即为 `n + D/2`：

- **成功**：对增量进行二分递增：`D/2/2`、`D/2/2/2`……
- **失败**：对增量进行二分递减：`-D/2/2`、`-D/2/2/2`……

依此规则持续迭代：成功后递增，失败后递减，直到收敛的*增/减量*达到设定的精度（如**5**秒）以下，最后一次成功的值即为结果值。

精测流程示意（伪代码）：

```go
// 粗测结果 4.5m（270s）
// 粗测最后一次失败 5m（300s）
// 假设精度 5s
// D: 300-270 = 30s
285s => 成功 =>     // 270 + (30/2) => 增量 15
292.5s => 成功 =>   // 285 + (15/2) => 增量 7.5
296.25s => 成功 =>  // 292.5 + (7.5/2) => 增量 3.75
Done => 296.25s     // 精度已完成：3.75 < 5
```

```go
285s => 成功 =>     // 增量 15
292.5s => 失败 =>   // 增量 7.5
288.75s => 成功 =>  // 292.5 - (7.5/2) => 增量 -3.75
Done => 288.75s     // 精度已完成：|-3.75| < 5
```

**注**：减量为负增量值，取绝对值对比精度要求。

```go
285s => 成功 =>     // 增量 15
292.5s => 失败 =>   // 增量 7.5
288.75s => 失败 =>  // 292.5 - (7.5/2) => 增量 -3.75
End => 285s         // 精度已完成：|-3.75| < 5
```

```go
// 粗测成功值 270s
285s => 失败 =>     // 增量 15
277.5s => 失败 =>   // 增量 -7.5
273.75s => 失败 =>  // 增量 -3.75
End => 270s         // 精度已完成：|-3.75| < 5
```


### 可分离性

粗测和精测是可以分离的两个独立的探测周期（从*Step.0*开始），可以不必在同一服务器上进行。

实际上，探测全程由客户端主导，服务器只需根据请求提供响应即可（`STUN:Live.Port`、`STUN:Addr` 和 `STUN:Live`）。


### 配置

*起始间隔*、*精测精度*应可由用户配置，以强化对不同网络的适应性。

> **提示：**
> 移动网络的NAT存活期较短，但起始间隔通常不应低于10秒。
