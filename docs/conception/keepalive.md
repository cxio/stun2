# NAT映射存活期探测

NAT映射有存活期，通讯静默超时后NAT映射会失效，对某些应用来说，这个存活期可能很重要。

客户端与服务器间的通信采用 *QUIC 安全连接 & 底层 UDP Socket 复用* 模式，其中 QUIC 用于安全传输，底层裸 UDP 用于 NAT 映射探测。


## 前提条件

服务端运行一个存活期探测服务 quic.Listener，由一个已经存在的 net.UDPConn 创建。

> **实现：**
> 参见 quic-go 库的 `quic.Transport{Conn: udpConn}` 用法。


## 预探测（`STUN:Addr`）：Step.0

客户端创建到服务器的普通 UDP 拨号连接（net.UDPConn），并基于此连接创建一个 QUIC 拨号（quic.Conn）连接。

这样就创建了客户端到公网的 NAT 映射，然后客户端执行如下操作：

1. 向服务器请求自身公网映射地址（`STUN:Addr` => `IP:Port`）。
2. 检查映射地址与自身本地地址是否相同（含端口），从而确认自己是否处于 NAT 之内。

如果客户端处于 NAT 之内，则继续下面的流程，否则结束。

> **注：**
> 获取到的端口号（`Port.0`）会被暂存，将在后续步骤中被使用。


## 客户端：Step.1 创建新 QUIC 连接

1. 客户端关闭与服务端的 QUIC 连接（仅 quic.Conn），从 QUIC 安全连接退化到原普通的裸 UDP 通讯链路（保留 net.UDPConn）。
2. 使用一个新的随机端口向同一服务节点拨号，创建一个新的 QUIC 安全连接。

至此，客户端和服务器之间创建了两条通讯链路：

- 裸 UDP 旧连接：用于接收服务端发送的探测消息。
- 新 QUIC 连接：用于客户端向服务器发送请求（携带数据），让服务器在旧连接上发送探测消息。

> **设计说明：**
> 客户端必须用一个新端口拨号创建 QUIC 连接，发送探测请求，
> 否则如果从旧链路上的发送请求，就会刷新 NAT 映射计时器，服务端的探测包就没有了意义。
>
> 与传统探测不同，延时不由服务器控制，而是客户端全权掌控探测节奏。服务器仅需简单即时操作即可。
> 这极大的简化了服务器端的逻辑，也更合理。


## 客户端：Step.2 请求服务器发送探测

在新的 QUIC 安全连接上，客户端向服务器请求存活期探测（`STUN:Live`）。发送的数据包括：

- Key32：会话密钥，32字节随机序列。每一次 `STUN:Live` 时都可以不同。
- Port.0：裸 UDP 连接上的旧端口号，即 `STUN:Addr` 请求时创建的 NAT 映射端口。

客户端在 `Port.0` 上侦听，收到消息后验证并回应。服务器的探测包和客户端的回应包数据为会话标识SN（详见下文），在裸 UDP 连接上发送。

客户端的回应会刷新 NAT 映射（计时器重置），记录此时间，作为下一次 `STUN:Live` 请求的计时起点。

> #### 客户端判断
> - 如果收到回应，表示映射没有改变，依然有效。
> - 如果没有收到回应（12秒超时），表示映射已经改变，回应不可达。


### 会话标识

客户端与服务器之间发送的数据为会话标识（SN），是一个有着内在构造规则的字节序列。

**SN**的构造规则如下（伪代码）：

```go
// Rnd16: 16字节随机序列。
// Rnd16[0]: 首字节高两位置零，标识非 QUIC 数据包。
// 注意：
// 虽然QUIC会话会关闭，但服务端普遍监听，依然需要这一清位分辨。
Rnd16[0] &= 0x3F

// LocalIP:
// - 客户端：自己的公网IP，服务端可通过UDP连接获取。
// - 服务器：服务器IP。客户端已知服务器IP，可执行验证。
// TmpN: 变长随机字节序列，用于隐藏 SN 的长度特征。长度：464 ~ 1024
// 前段固定 16 + 32 = 48 字节。
SN = Rnd16 + HMAC_SHA256(Key32, Rnd16 + LocalIP + TmpN) + TmpN
```

> #### 附：SN 验证
> - 从 SN 提取各片段：Rnd16, Hash32, TmpN。
> - 对端公网IP已知，验算SN合法性：HMAC_SHA256(...) == Hash32。

服务器和客户端各自构造自己的会话标识SN，作为消息内容发送，收到消息的对端根据规则进行验证。


### 服务端操作

1. 在新 QUIC 连接上提取客户端的IP，以及传递来的旧端口号 `Port.0`，构造目标地址 `IP:Port.0`。
2. 在旧连接（裸UDP）上向该地址发送消息，数据内容为 SN 。

服务器发送的消息遵循指数退避策略，初始间隔从 100ms 开始，逐次加倍直到收到回复或超时。

间隔时间（ms）：100, 200, 400, 800, 1600, 1600, 1600, 1600, 结束。
累计时长（ms）：100, 300, 700, 1500, 3100, 4700, 6300, 7900, 结束。

> **注意：**
> 每一次发送的 SN 都是即时新建的，以避免链路中间件的优化合并或丢弃。

服务端的操作逻辑十分简单：收到请求，构造目标地址和SN、发送消息；接收回应，及时终止冗余发送。


### 附：探测原理

前一次的 `STUN:Live` 成功交互，是下一次 `STUN:Live` 交互的计时起点。两者的间隔时间即为 NAT 映射的存活期探测值。

客户端会连续尝试多个间隔时间（递增）请求服务端发送消息，直到某次 `STUN:Live` 请求的探测包超时，说明 NAT 映射已经失效，此时前一次成功交互的间隔时间即为 NAT 映射的存活期。


## 探测循环（客户端 <=> 服务器）

在一个探测周期内，客户端多次向服务器请求 `STUN:Live` 探测（Step.2）。

客户端超时设置为**12**秒，如果在 12 秒内没有收到服务器的任何回应，即可断定该次探测为失败。


### 粗测

粗测是一个快速的探测流程，目的是快速获得一个大致的存活期范围。客户端在粗测阶段会尝试较大的时间间隔，以快速缩小存活期范围。

在粗测周期内，客户端的 `STUN:Live` 请求时间间隔为2倍增量模式：从 `15s`（可配置）开始，然后间隔 `30s`、`60s`、`120s` ...，直到超时或设定的最长间隔终止。

> **注：**
> 低于起始间隔时间（如15秒）的生存期的NAT映射不作探测。
> 间隔时间完全由客户端控制，服务器仅在收到 `STUN:Live` 请求后才发送探测包。


### 精测

粗测成功之后，得到的存活期时间粒度太粗，此时即可启动精测流程。

精测从粗测获得的有效间隔开始，按二分规则进行增减时间探测。假设粗测的有效间隔为 `n` 秒，精测初始间隔时间即为 `n + 0.5n` 秒：

- 如果成功，则对增量进行二分递增（总值 `n + (0.5 + 0.25)n`）。
- 如果失败，则对增量进行二分递减（总值 `n + (0.5 - 0.25)n`）。

依此规则持续探测：成功后继续递增，失败后继续递减，直到*增量/减量*达到设定的精测粒度（如5秒，可配置）以下，即停止。


### 可分离性

粗测和精测是可以分离的两个独立的探测周期（从 Step.0 开始），可以不必在同一服务器上进行。

实际上，探测全程由客户端主导，服务器只需提供 `STUN:Addr` 和 `STUN:Live` 服务即可。


## 配置

*起始间隔*、*精测精度*、*终点时长*（最大间隔）应可由用户配置，以强化对不同网络的适应性。

> **提示：**
> 移动网络的NAT存活期较短，但起始间隔通常不应低于10秒。
