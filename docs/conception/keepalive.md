# NAT映射存活期探测：`STUN:Live`

客户端的 NAT 映射有流状态存活期逻辑，通讯静默超时后 NAT 映射会失效。对某些应用来说，知道这个值可能很重要。

与 STUN:Cone 探测类似，客户端与服务器间的通信采用 *QUIC 安全连接 & 底层 UDP Socket 复用* 模式，其中 QUIC 用于安全传输，底层裸 UDP 用于 NAT 映射探测。


## 前提条件

- 服务端启动后创建了一个**32**字节的随机密钥 `BaseKey`，用于所有的会话验证。
- 服务端运行一个存活期探测服务 `quic.Listener`，由一个已经存在的 `net.UDPConn` 创建。

> 客户端与服务器之间的 QUIC 通讯采用 Stream 模式。
> 本设计假设网关 NAT 持续正常运行，网关异常不在本协议考虑范围。


## 会话标识

客户端与服务器之间在纯 UDP 链路上发送的消息包为会话标识 `SN`。结构与 `STUN:Cone` 协议中的 `SN` 类似，但稍有不同：

```go
// Rnd16: 16字节随机序列。
// Rnd16[0]: 首字节高两位置零，标识非 QUIC 数据包。
Rnd16[0] &= 0x3F

// domainTag:
// - 服务器："Server@STUN:Live"
// - 客户端："Client@STUN:Live"
// TmpN: 变长随机字节序列，用于隐藏 SN 的长度特征。长度：16 ~ 1024
// 前段固定 16 + 32 = 48 字节。
SN = Rnd16 || HMAC_SHA256(Key32, domainTag || Rnd16 || TmpN) || TmpN
```


### SN 验证

```go
// SN 解构
Rnd16 := SN[:16]
TmpN  := SN[48:]
Hash  := SN[16:48]

// 是否通过验证
return Hash == HMAC_SHA256(Key32, domainTag || Rnd16 || TmpN)
```


## 预探测：创建 NAT 映射

客户端创建到服务器的普通 UDP 拨号连接（`net.UDPConn`），并基于此连接创建一个 QUIC 连接。这样就创建了客户端到公网的 NAT 映射。

然后客户端向服务器发送预探测请求 `STUN:Live.Port`，包含数据：

- Version:  版本号（初始值 1）。
- Distance: 初始时间窗口（秒数），含初始间隔时间 + 适当余量。余量**2~3**分钟即可。

服务器收到请求后，返回响应：

- `ClientAddr`: 客户端公网映射地址（IP:Port）。
- `Validation`: 客户端探测有效性证明。

```go
// 时间戳为证明的有效截止时间，
// Unix 时间，单位：秒；变长整数（ULEB128 最简编码）
Timestamp := Encode( Now + Distance )

// @domainTag: STUN:Live.Port
Validation := Timestamp || HMAC_SHA256( BaseKey, domainTag || ClientAddr.IP || ClientAddr.Port || Timestamp )
```


### 初步判断&准备

客户端比较返回的映射地址与本机地址（含端口）：

- **相同**：`Open Internet` | `UDP Firewall`，无需继续，结束。
- **不同**：流程继续……

确认自己处于 NAT 内之后：

- 暂存获取到的自己的公网地址 `ClientAddr`。
- 暂存服务端派发的批准证明 `Validation`，后续需要此批条证明目标地址。


## 正式探测

### Step.1 创建新 QUIC 连接

**客户端**关闭之前与服务器的 QUIC 连接（仅 quic.Conn），退化到纯 UDP 链路。
**客户端**使用一个*新的*随机端口向同一服务节点拨号，创建一个新的 QUIC 连接（新的 Socket，正常 keep-alive）。

至此，客户端和服务器之间有了两条通讯链路：

1. 裸 UDP 旧连接：用于接收服务端发送的探测包。
2. 新 QUIC 连接：用于客户端与服务器通讯：发送 `STUN:Live` 请求，让服务器在旧连接上发送探测包。

客户端关闭 QUIC 连接之，等到该路径上因关闭而产生的发送全部结束后，即记录首次*探测间隔*的起始时间 `Time.0`。

> **注意：**
> 旧链路从 `Time.0` 起必须完全静默，包括客户端和服务器双方，避免残留的 Transport 可能回 Stateless Reset 而续活映射。

> **设计：**
> 与传统探测不同，本设计中延时不由服务器控制，客户端掌控所有探测节奏。服务器简单响应即可。
> 这简化了服务器端的逻辑（极简状态），也让客户端更灵活，可自由控制精度。
>
> 另外，探测流程不要求控制通道（QUIC）与被探测映射相同公网 IP。控制连接断开即丢弃本轮，不把上次成功间隔记为存活期；若要继续，从「*预探测：创建 NAT 映射*」重新开始。

最后，客户端在 `ClientAddr.Port` 上启动（或继续）侦听。注意侦听是复用旧的 Socket 继续读，而非新建绑定。


### Step.2 请求服务

当预设的间隔时间到达后，客户端即在新的 QUIC 连接上向服务器发送 `STUN:Live` 请求：

- Version:    版本号（初始值 1）。
- Key32:      即时生成的会话密钥，32字节随机序列。**注**：每次都不同。
- Address:    纯 UDP 连接上的旧地址（即之前暂存的 `ClientAddr`）。
- Distance:   新的时间窗口大小（秒数）。即至下一次 `STUN:Live` 请求前的时长 + 余量。
- Validation: 之前暂存的服务器派发的批准证明。

> **注**：服务器收到请求后的操作见 [下文](#服务端)。

客户端在 `ClientAddr.Port` 上侦听，收到服务器发送的探测包（`SN`）后，验证并回应：

- 回应数据包也为即时构建的 `SN`。
- 收到一个回应一个（最多8个），同时更新*探测间隔*的起始时间 `Time.0`。

> **探测间隔：**
> 本次 `Time.0` 到下一次 `STUN:Live` 请求的时间间隔。也即待确认的 NAT 映射生存期。

服务器会在 QUIC 连接上返回新的探测证明 `Validation`，客户端应及时更新暂存。


#### 状态判断

对于客户端在 `ClientAddr.Port` 上的侦听来说：

- 如果收到探测包，表示映射没有改变，原映射端口依然有效。
- 以新收到 Validation 时为起点，如果**10**秒超时（*不可配置*）没有收到探测包，则表示映射已经改变，探测不可达。


## 服务端

服务器监听并接收任意客户端的 `STUN:Live` 请求，根据发送来的数据：

- 验证其 `Validation` 的有效性。
- 根据客户端的 `Distance` 申请，重新创建 `Validation`（最长不超过**45**分钟）并返回给客户端。
- 向目标地址 `Address`，发送探测包（`SN` 即时构建）。

**注意**：探测包需从 quic.Listener 的同一**IP:Port**发出。

**约束**：同一目标地址的 STUN:Live 请求最小间隔为 `10s`（*不可配置*），避免频繁请求消耗服务器资源。


### 验证 Validation 和 Address

```go
// 提取时间戳
Timestamp := Validation[0:len(Validation)-32]

// 是否有效期内：
if Now.Timestamp > Decode(Timestamp) {
    return false // 证明过期
}
// 有效载荷
Valid32 := Validation[len(Timestamp):]

// 目标是否合法：
// @domainTag: STUN:Live.Port
// Address 客户端传递来的目标地址
return Valid32 == HMAC_SHA256(BaseKey, domainTag || Address.IP || Address.Port || Timestamp)
```


### 更新探测证明 Validation

```go
// Distance 客户端申请窗口（≤45分钟）
Expire := Now.Timestamp + Distance
Timestamp := Encode( Expire )

// 新的有效期证明
// @domainTag: STUN:Live.Port
Validation := Timestamp || HMAC_SHA256( BaseKey, domainTag || Address.IP || Address.Port || Timestamp )
```

服务器在 QUIC 连接上将更新后的 `Validation` 发给客户端，然后在纯 UDP 链路上发送 `SN`……直到收到客户端回应或冗余发送结束。


### 发送频率

服务器发送的消息遵循指数退避策略，初始间隔从 100ms 开始，逐次加倍直到 1600ms，然后固定发送……直到收到客户端回复或自然结束。

间隔时间（ms）：100, 200, 400, 800, 1600, 1600, 1600, 1600 结束。
累计时长（ms）：100, 300, 700, 1500, 3100, 4700, 6300, 7900 结束。


### 极简状态

服务端依赖批准证明 `Validation` 验证客户端请求的合法性，无需存储客户端的任何信息，仅暂存 `Key32` 用于构造 `SN` 和验证客户端的回包（终止通知）。

这是一种极简状态的逻辑，服务器的操作十分简单：

- 收到请求，验证&构造目标地址。
- 即时创建 `SN` 并发送……
- 接收远端回应，验证并终止后续冗余发送。

服务器验证客户端回包（`SN`）的逻辑参考上面 [§.SN 验证](#sn-验证) 章节。


## 探测循环（客户端 <=> 服务器）

在一个探测周期内（同一轮），客户端需多次向服务器请求 `STUN:Live` 探测，每次从 **§.Step.2 请求服务** 开始。

客户端在 `ClientAddr.Port` 上侦听探测包，如果直到超时没有收到服务器的探测包，即可*终止*本轮探测。上一次成功交互的探测间隔时间即为有效。这与控制连接断开不同：后者不产出存活期。

服务端如果未收到客户端的*结束发送*通知回包，则发送完 8 次后自然结束（无超时）。

在完整一轮探测结束之后（映射探测超时，或控制连接断开），客户端可能需要重新开始新一轮测试，这需要从 `§.预探测：创建 NAT 映射` 开始。


### 附：探测原理

在同一轮中，首次间隔的 `Time.0` 是旧路径关闭残留发送结束的时刻；其后每一次 `STUN:Live` 的最后回包时刻更新 `Time.0`，作为下一次请求的计时起点。两者的间隔时间即为 NAT 映射的存活期探测值。

客户端和服务器会在这个间隔期内，在旧的纯 UDP 链路上保持完全静默，避免任何一方刷新 NAT 映射计时器。

客户端会连续尝试递增的多个间隔时间，向服务器发送 `STUN:Live` 请求，直到某次的探测包超时（NAT 映射失效）。此时前一次成功交互的*探测间隔*时间即为有效……

**注**：详细探测流程请参考下面的「粗测」和「精测」部分。


### 粗测

粗测是一个快速的探测流程，目的是快速获得一个大致的存活期值。

粗测的*起始间隔*是灵活的，用户应当根据自身所处环境，配置一个合适的折中值：

- **成功**：下一次间隔时间翻倍，直至探测失败。
- **失败**：回退上一次变化量（增量/减量）的一半。如果首次即失败，回退初始间隔的一半，即进入收敛期。
- **结束**：最后一次失败=>成功，结果为最后一次成功时的值。

> **特例：**
> 如果测试一直成功，直到超过服务端**45**分钟硬上限时，则取 40 分钟为生存期进行测试（系统默认5分钟余量）：
> - **成功**：40 分钟即为探测到的生存期。这是一个最大上限值，实际生存期可能更长。
> - **失败**：按上面失败规则回退变化量的一半，进入收敛期……直到结束。

下表伪代码示意了探测流程：

```go
// 假设起始间隔 3m
3m => 成功 =>   // 初始值
6m => 失败 =>   // 3*2 = 6
4.5m => 成功 => // 6 - (3/2) = 4.5
Done => 4.5m    // 结束
```

```go
// 假设起始间隔 2m
2m => 成功 =>   // 初始值
4m => 成功 =>   // 2*2 = 4
8m => 失败 =>   // 4*2 = 8
6m => 失败 =>   // 8 - (4/2) = 6
5m => 失败 =>   // 6 - (2/2) = 5
4.5m => 成功 => // 5 - (1/2) = 4.5
Done => 4.5m    // 结束
```

为避免不必要的收敛细分迭代（一直失败），用户可设置迭代**次数**上限：如果一直没有「失败=>成功」的转换，则取最后一次成功的值为结果。

```go
// 迭代次数上限 5
2m => 成功 =>   // 初始值
4m => 成功 =>   // 2*2 = 4
8m => 失败 =>   // 4*2 = 8
6m => 失败 =>   // 8 - (4/2) = 6
5m => 失败 =>   // 6 - (2/2) = 5
End => 4m       // 抵达上限约束，取上面最后一次成功时的值
```

首次即失败（配置值不恰当）：

```go
// 初始间隔 5m
5m => 失败 =>   // 初始值
2.5m => 成功 => // 5 - (5/2) = 2.5
Done => 2.5m    // 结束
```

如果首次即失败，且一直失败，则可能是配置值过高，且设置了较低的迭代次数上限。用户应当修改配置。如果配置值不高且迭代次数也不低，则可判定为异常。用户可以尝试向不同的服务器节点请求服务。

从上面的示例可以看出，恰当的初始配置值可以显著优化请求次数，缩减总的探测时间。

> **注意：**
> 每一次失败之后的再次探测尝试，需要从「*§.预探测：创建 NAT 映射*」开始。下面「精测」部分也同。


#### 使用提示

如果客户端粗测持续成功……直到抵达次数上限而终止，通常说明配置可能有问题：

- 用户应先修改配置：增大起始间隔，或提高迭代次数上限再重试。
- 如果依然如此，则可能是网关的 NAT 映射存活期超长，或本机实际上处于公网。此即无需探测。

此状况下，客户端无法进入精测阶段（无收敛目标）。用户需先探明原因解决之后，才有必要继续。


### 精测

粗测成功之后，如果觉得时间粒度太粗，可启动精测流程。

精测在粗测的基础上进行，对粗测中最后一次失败和成功的时间差，按二分规则增减时间探测。假设粗测的存活期为 `n`，最后一次失败时为 `M`，则待探测时长为 `D = M-n`，精测初始间隔时间即为 `n + D/2`：

- **成功**：对增量进行二分递增：`D/2/2`、`D/2/2/2`……
- **失败**：对增量进行二分递减：`-D/2/2`、`-D/2/2/2`……

依此规则持续迭代：成功后递增，失败后递减，直到收敛的*增/减量*达到设定的精度（如**5**秒）以下，最后一次成功的值即为结果值。

精测流程示意（伪代码）：

```go
// 粗测结果 4.5m（270s）
// 粗测最后一次失败 5m（300s）
// 假设精度 5s
// D: 300-270 = 30s
285s => 成功 =>     // 270 + (30/2) => 增量 15
292.5s => 成功 =>   // 285 + (15/2) => 增量 7.5
296.25s => 成功 =>  // 292.5 + (7.5/2) => 增量 3.75
Done => 296.25s     // 精度已完成：3.75 < 5
```

```go
285s => 成功 =>     // 增量 15
292.5s => 失败 =>   // 增量 7.5
288.75s => 成功 =>  // 292.5 - (7.5/2) => 增量 -3.75
Done => 288.75s     // 精度已完成：|-3.75| < 5
```

**注**：减量为负增量值，取绝对值对比精度要求。

```go
285s => 成功 =>     // 增量 15
292.5s => 失败 =>   // 增量 7.5
288.75s => 失败 =>  // 292.5 - (7.5/2) => 增量 -3.75
End => 285s         // 精度已完成：|-3.75| < 5
```

```go
// 粗测成功值 270s
285s => 失败 =>     // 增量 15
277.5s => 失败 =>   // 增量 -7.5
273.75s => 失败 =>  // 增量 -3.75
End => 270s         // 精度已完成：|-3.75| < 5
```

> **提示：**
> 精度（如5秒）是两轮测试生存期的差值，不是生存期本身。不会与 `7.9s` 冗余发包总时长冲突。


### 可分离性

粗测和精测是可以分离的两个独立的探测周期（从 *§.预探测：创建 NAT 映射* 开始），可以不必在同一服务器上进行。

实际上，探测全程由客户端主导，服务器只需根据请求提供响应即可（`STUN:Live.Port` 和 `STUN:Live`）。


### 配置

*起始间隔*、*精测精度*应可由用户配置，以强化对不同网络的适应性。

移动网络的 NAT 存活期较短，但起始间隔时间不能低于**10**秒（超出服务端冗余发送时间总长 `7.9s` 加一点余量）。
