# NAT 类型/层级探测：`STUN:Cone`

客户端首先需要连入STUN服务网络，获取多个服务节点的联系信息，其中包含建立安全 QUIC 所需的如 `SPKI`、`ECH` 公钥等。
详见 [cxio/p2p 项目](https://github.com/cxio/p2p)。

然后客户端就可以与这些服务节点建立连接，并请求探测服务。

> **技术栈：**
> 客户端与服务器间的通信采用 *QUIC 安全连接 & 底层 UDP Socket 复用* 模式，其中 QUIC 用于安全传输，底层裸 UDP 用于 NAT 映射探测。
> Go 语言实现，使用 quic-go 库，参考 `quic.Transport{Conn: udpConn}`, `Transport.ReadNonQUICPacket()` 等用法，外部传入 `net.UDPConn`。


## 准备

节点首先应当确认自己是否位于 UDP 被封禁的网域：尝试与服务节点建立 QUIC 连接，如果连接成功，则进入下一步，否则继续尝试。如果多次尝试都失败，那大概率 UDP 被封禁（`UDP Blocked`），NAT 探测无意义。

> **提示：**
> 如果已经与服务器建立TCP连接（确定在线），可直接请求其UDP监听地址并尝试连接。
> 因为网络分享的服务器节点信息并不完全可用，所以该选项有更高的优先级。


## 预探测（Step.0）

当确认自己的 UDP 链路可用后，客户端向多个服务节点请求获取自身公网地址（`STUN:Addr`），检查返回结果：

> **说明：**
> 客户端需要复用同一个底层 UDPConn 向多个服务器建立 QUIC 并请求 `STUN:Addr` 服务。
> 客户端向多个服务器请求 `STUN:Addr` 的成功返回数量应当不少于**3**个（可配置）。

提取返回地址中的端口（`Port`）：

- 如果多个端口都不同，确定为 `Sym-Like`，结束探测。
- 如果多个端口有部分不同，也视为 `Sym-Like`，保守处理，结束探测。
- 如果所有端口都相同，即视为 `非 Sym-Like`，进入下一步……

返回地址与客户端本地地址对比（IP:Port 全等比较）：

- 相同（Y）：`Open Internet` | `UDP Firewall`，待进一步确认。
- 不同（N）：待正式探测，进一步判断……

> **实现：**
> 这是属于应用程序的实现逻辑，本库只做出规范说明，不作实现。
> 注意客户端应当在获取服务端返回公网地址后，主动关闭 QUIC 连接（通知服务器释放资源）。


## 正式探测

客户端向任意一台服务节点请求 NAT 类型探测服务（`STUN:Cone`）。注意此时为 QUIC 安全连接。

> **提示：**
> - 如果服务端无法提供探测服务（比如自己连接的受托服务器不足），会返回状态告知。
> - 客户端也可以尝试本流程多次以提高探测结果可靠性（并发需走不同 UDPConn）。
>
> 上面两项都属于应用层逻辑，本协议仅作提示，以帮助应用正确实现。


### 客户端（Step.1）

客户端的 `STUN:Cone` 请求中包含如下数据：

- Version: 版本号（初始值 1）。
- Key32：会话密钥（32字节），用于构建会话标识（SN）。
- Exclist：排除清单，包含节点自己近期（比如半小时）曾经连接过的远端服务器IP。

> **解释：**
> `NewHost` 消息需要一个近期未曾与客户端连接过的新IP，因此需要排除清单（`Exclist`）。
> 半个小时的时间窗口已经足够，因为没有哪个NAT映射会闲置这么久而不关闭。

服务端收到信息后，即可通知客户端关闭 QUIC 连接，回退到该 QUIC 连接的底层普通 UDP 连接（UDPConn）上通讯。

> **提示：**
> 服务器也可关闭 QUIC 连接，但仅限 QUIC 会话层面。

> **注意：**
> 如果客户端提交过大的 Exclist，服务器可能拒绝为其服务。
> 作为一种良好的实践，客户端应当在初始上线时即请求NAT探测服务。


### 会话标识

服务器向客户端发送的探测消息是一个会话标识（SN），它有着内在的构造规则。

**SN**的构造规则如下（伪代码）：

```go
// Rnd16: 16字节随机序列。
// Rnd16[0]: 首字节高两位置零，标识非 QUIC 数据包。
// Rnd16[0]: 首字节的低1位用于标记消息发送源（服务端）：
// - 0: NewPort 同机新端口发送
// - 1: NewHost 新主机发送
// from: NewPort | NewHost
// 设计：
// 明文会话标识尽可能不含特征魔数，避免数据包被定向销毁（丢弃）。
// （bit7=0 / bit6=0 / bit5..bit1=随机 / bit0=from）
Rnd16[0] = Rnd16[0] & 0x3E | from

// 仅限服务端。
// Key: 会话密钥（Key32）或会话密钥封装（见后）。
// TmpN: 变长随机字节序列，用于隐藏 SN 的长度特征。长度：464 ~ 1024
// 前段固定 16 + 32 = 48 字节。
SN = Rnd16 + HMAC_SHA256(Key, Rnd16 + TmpN) + TmpN
```

> **设计：**
> SN 构造中没有服务端地址，因为对客户端来说，受托服务器未知——即无法验证 SN 的合法性。
> 另外，客户端不会回复消息包，无需设置防重放措施。服务端发送的SN也无需考虑重放攻击，
> 因为此时的重放攻击，实际上是攻击者充当了义务受托服务器而已。


### 服务器（Step.2）

在服务器通知客户端关闭 QUIC 连接，并收到客户端的关闭确认后，执行如下操作：

- `NewPort`: 用一个新的随机端口向客户端发送消息，数据为即时构造的 SN。
- `NewHost`: 从本机的另一个新IP或请求另一个服务器向客户端发送消息，数据 SN 即时构造。

> **实现：**
> NewPort 和 NewHost 应双路并发执行，客户端统一超时计时。

> **注意：**
> 服务器端使用的新 IP 必须与原连接的IP同簇（同为 IPv4 或 IPv6）。


#### 受托服务器

如果是请求另一个服务节点协助执行 `NewHost`（委托发包），会向其提供必要的客户端信息（`Notice`）：

- Version: 版本号（初始值 1）。
- 客户端公网映射地址（`IP:Port`）。
- 客户端的会话密钥封装 `SHA256( Key32 )`。
- 应用标识：应用层实现自身的标识（可选），用于区分支持此协作的不同应用实现。
- 应用数据：相应应用自身需要对额外数据，可选。

此时不会向受托服务器传递原始的客户端会话密钥，以强化安全性（冗余，但低成本）。

**受托配合**：受托服务器会执行 `NewHost` 操作：向目标客户端发送纯 UDP 消息，消息内容为相同规则即时构造的 `SN`。

> **注意：**
> 如果是源服务器从自己本机的一个新IP发送 `NewHost`，也需要用封装之后的会话密钥构造 SN。
> 因为客户端会借助于 `NewHost` 标识来判断会话密钥的实际值。

> **提示：**
> 委托服务器与受托服务器之间为安全连接（通常也为 QUIC）。


#### 消息发送

服务器通过普通的裸 UDP 连接发送消息，需要实现冗余发送逻辑。考虑被利用作为 DDoS 攻击的可能性，NewHost 冗余发送的次数应尽量低。

- **NewPort**：共发送**5次**，间隔时间为：`100ms ~ 400ms` 随机选取。
- **NewHost**：共发送**3次**，间隔时间为：`100ms ~ 300ms; 400ms ~ 800ms` 区段内随机取值。

服务器按规则发送即可，不用等待客户端回应（实际上也没有回应）。

> **注意：**
> 每一次发送的 SN 都是即时新建的，以避免链路中间件的优化合并或丢弃。


#### 客户端超时

客户端在发出 STUN:Cone 请求后，其等待的超时综合考虑，设置为**5**秒。

如果在 5 秒内客户端一个包都没收到（`NewPort` | `NewHost`），即判定该探测项为失败。


#### 附：源服务器安全

无信任委托发包，可能被恶意的源服务器利用，创建 DDoS 攻击（3倍放大），因此这里需要一个安全防范或缓解措施。

在P2P的环境下，设计一种可信机制会很复杂。考虑简单性和效率，可以采用**工作量代价**来进行 DDoS 缓解：源服务器委托时需要提供一个工作量证明（`Equi-X`）。

受托发送的探测包数量并不高（固定3个），每一个攻击请求（委托）都需要提供工作量证明，所以这并不是一个高效的攻击方式（非优放大器）。

这属于服务器程序实现层面的逻辑（详见 [stun2p项目](github.com/cxio/stun2p)），本 STUN 协议仅提出建议（这是协议设计引出的问题，因此需要提出可能的解决路径）。


### 客户端（Step.3）

客户端读取收到的消息，提取发送源（`NewPort`|`NewHost`），并根据规则验证 SN 的有效性。

> **注意：**
> 如果是 NewHost 消息，HMAC 的密钥应为：`SHA256( Key32 )`。

如果核验通过，则为有效的探测包。因为服务端发包较少，且历时很短（理论上 1s，实际上可能 2~3s），故不设计客户端回应。


### 综合判断（Step.4）

客户端根据 `NewPort` 和 `NewHost` 两个连入的情况，综合判断自身 NAT 类型或所在网域。

**NewPort**:
- 收到 => `RC | FullC`。**注**：`FullC` 在 NewHost 段确认&覆盖。
- 超时 => `P-RC | Sym-Like` => `P-RC`。**注**：`Sym-Like` 已在预探测中确认并排除。

**NewHost**:
- 收到 + 预探测.N => `FullC`。
- 收到 + 预探测.Y => `Open Internet`，即 `Public`。
- 超时 + 预探测.Y => `UDP Firewall` 网域。

> **应用层优化：**
> 如果 NewHost 先收到消息，NewPort 的超时等待可以提前结束。
> 也即：如果当前收到消息后已经可以做出判断，即可终止其它等待。


### 附：判断矩阵

> **注：**
> 不含 `Sym-Like` 条目，其已在预探测阶段完成。

| NewPort 收到 | NewHost 收到 | 与本地地址相同 | 结果 |
|:---:|:---:|:---:|------|
| * | Y | N | Full Cone |
| Y | N | N | RC |
| N | N | N | P-RC |
| * | Y | Y | Open Internet（Public） |
| * | N | Y | UDP Firewall |

**说明：**
- `N` 表示否定（No）。
- `Y` 表示肯定（Yes）。
- `*` 表示无需考虑，N/Y 皆可。
