# 文档结构

本文档在 `docs` 目录之下，因此子目录相对于此目录，不再从项目根目录表达路径。


## 目录设计

项目文档分为四个层级：前两个层级由用户主导，后两个层级由 AI 生成：

| 层级 | 目录 | 作者 | 说明 |
|------|------|------|------|
| Conception（设计构想） | `conception/` | 人工 + AI 辅助 | 定义项目想做什么，以及为什么。包含作者的思考、探索，问题的边界以及可能的选择等。 |
| Decision（架构决策） | `decision/` | AI + 人工互助 | 定义目标的解决方向、方式，构想没有明确的技术选型、必要的细节等。 |
| Spec（技术规格） | `spec/` | AI 生成 + 人工审阅 | 定义目标具体什么样，精确的技术规格。遵从 Conception 和 Decision。 |
| Plan（实施计划） | `plan/` | AI 生成 + 人工复核 | 明确 Spec 怎么编码实现，按阶段实施的计划（TDD 任务、包边界、文件清单等），可追溯自 Spec。 |


### 权重关系

**权威顺序**：`Conception` + `Decision` > `Spec` > `Plan` > Implementation。


### 反馈回路

上面的权威顺序也是逻辑关系，同时也是工作流。如遇冲突应以上层为准：

- 如果在实现（Implementation）时发现逻辑走不通，有问题，应当回到 Plan 层进行检查，并逐步向上递推。
- 如果在写 Plan 时发现某个 Spec 根本实现不了，应回退到 Spec 层进行调整（而不是在 Plan 中悄悄自定规格），Plan 需遵循 Spec 层定义。
- 如果在写 Spec 时发现目标不合理或不恰当，应当回退到 Decision 甚至 Conception 层核实，并报告用户。
- Decision 是 Conception 的选择和细化，需要人类参与。问题至此则由人类作者重新审视、修订，甚至改写初始的构想，并重新决策。

也即：正常的流程是自上而下，但如果出现问题，则需逆流而上，逐层检查。当上层完善确定之后，即可再向下修订同步，或重新生成。


### 排除目录

`plans/`（带 s）用于 AI Agent 工作过程中的临时实施计划，不作为正式文档的一部分；正式计划在 `plan/`。

另外，上级目录中的 `working/` 属于工作间目录（如果有），存放临时杂物，也不在正式文档序列里。


## 维护规则（Agent）

四个子目录分别存放了项目的设计构想、决策、技术规格和实施计划的文档。

- 设计构想: `conception/`
- 架构决策: `decision/`
- 技术规格: `spec/`
- 实施计划: `plan/`

当读取、创建或修改触及相应部分，请读取并参考其中的 `AGENTS.md`，如果有必要，请更新其中的文件清单。
