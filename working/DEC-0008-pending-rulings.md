## 待裁决项

### R1 信封 Version 的作用域（阻塞）

`SPEC-0001` §2 自相矛盾：一处写「各方法的 Version 独立演进」，另一处规定「先读 Version，不支持则回 `UnsupportedVersion` 并停读；再读方法名」。服务器在读到方法名之前无法知道该方法支持哪些版本，按方法判断版本在此解析顺序下不可实现。当前所有方法均为 v1，问题潜伏；任一方法升到 v2 即卡死。

- **方案 A（推荐）**：Version 为**协议全局版本**，删除「各方法独立演进」。信封字节布局不变，解析顺序不变。方法集的增减靠 `UnknownMethod`，不靠版本。
- **方案 B**：解析顺序改为先 Method、后 Version，保留按方法演进。信封布局不变（Version 仍在前），但服务器须先缓存 Version、读完 Method 再校验。

推荐 A 的理由：本协议的方法集小且方法名自带语义，按方法分版本带来的组合状态（8 个方法 × 各自版本）远超收益；而 B 会让「未知方法」与「不支持版本」的判定顺序反直觉。

落点：**DEC-0002**（信封形态）+ SPEC-0001 §2。

> 用户裁决：接受方案 A。

### R2 `STUN:Live` 的 `Distance` 语义（阻塞）

构想 `keepalive.md` 把 `Distance` 定义为「至下一次 `STUN:Live` 请求前的时长 + 余量」。但粗测规则是**成功后下一间隔翻倍**，而客户端发出第 N 次请求时尚不知本次成败，必须按「若成功」的分支预留窗口。即 `Distance` 需覆盖 `min(2*current, 40min) + 余量`，而非 `current + 余量`。

照字面实现的后果：第 N+1 次请求必因批条过期被拒，且（在 R3 未裁决前）极可能被当成「映射已失效」，于是每轮粗测都在第二次停下、报出等于起始间隔的假存活期，**且不报错**。

同时须补写一层从未出现的耦合：**45 分钟 Validation 上限 = 40 分钟探测上限 + ≤5 分钟余量**。两个常量各自散落在 `SPEC-0001` §10 与 `SPEC-0004` §3，约束关系无一处说明；正是这层关系保证了 `2*current` 封顶后仍签得出批条。

- **方案 A（推荐）**：在构想里把 `Distance` 明确为「覆盖下一次请求前的最大可能间隔 + 余量」，并写出与 40/45 分钟的耦合。
- **方案 B**：改为服务端按固定上限（2700s）签发，客户端不再申请窗口，`Distance` 字段退化或删除。省掉一处客户端易错点，代价是批条有效期一律 45 分钟，放宽了持票期。

落点：**Conception `keepalive.md`**（语义澄清，属构想层）+ SPEC-0004 §1、SPEC-0001 §10。

> 用户裁决：已在 keepalive.md「§Step.2 请求服务 > 关于 Distance」部分解释。

### R3 控制面拒绝与「映射失效」的区分（阻塞）

服务端**发**什么已经规定清楚（`RateLimited` / `VerifyFailed`，SPEC-0004 §4.1），缺的是客户端**据此产出什么**。这不是一般的错误处理细节，而是三个兄弟分支只覆盖了两个：

构想已经明确区分了其中两个——

```223:223:docs/conception/keepalive.md
客户端在 `ClientAddr.Port` 上侦听探测包，如果直到超时没有收到服务器的探测包，即可*终止*本轮探测。上一次成功交互的探测间隔时间即为有效。这与控制连接断开不同：后者不产出存活期。
```

`SPEC-0004` 末尾也照此落实了「映射超时用上一次成功间隔；控制断开不使用该间隔」。但**第三种输入——控制面返回 Status≠0——两处都没提**。它与前两者同族（都是「本次探测没能测出东西」），却是唯一没有归属的一种。

要紧之处在于三者的输出不同：超时把当前间隔写进 `lastFail`、喂给二分、最终变成上报的存活期；控制断开不产出；而 Status≠0 若被误归进第一类，库就会返回一个**貌似合理的错误数值且不报任何错**。判据是「该分支是否改变对外输出值」，不是「是否需要写错误处理」。

- **方案 A（推荐，最小改动）**：`SPEC-0004` §2.4 补一句——收到 Status≠0 即中止本轮、不产出存活期（语义等同控制连接断开）。一句话，不引入新机制。
- **方案 B**：在 A 之上再区分「批条过期」（见 R11 的 `ErrExpired`），使客户端只重取批条、保住已积累的 `lastSuccess` / `lastFail`，而不是丢弃整轮。

A 与 B 的差别只在代价：粗测走到第 5 步时批条过期，方案 A 会丢掉前面 4 步（可能已耗时一小时）。但若 R2 把 `Distance` 定对，正常流程下批条不会过期，B 就退化成时钟偏移的安全网——因此 **B 可以延后，A 不能**。

落点：**SPEC-0004 §2.4**（方案 A 属 Spec 补齐，无需动 Decision）；方案 B 随 R11 一并裁决。

> 用户裁决：同意方案 A。Distance 已在 R3 裁决中明确。

### R4 服务端 Live 非 QUIC 读取与分发（阻塞）

服务端如何接收客户端的回包 SN 从未规定：全部 `ReadNonQUICPacket` / `PushNonQUICPacket` 规定都在客户端侧，服务端只有一句「收到有效客户端 SN 即停」。这不能留给实现，因为两条已确立的约束在此冲突：`MEMORY.md` 第 4 条明确 Transport 只有**单一逻辑非 QUIC 读取点**，而 DEC-0005 第 2 项把 Key32 关在「该请求的处理协程」内，中间缺一层按源地址的分发。另外「首次调用前的到达包会被丢弃」意味着服务端必须**常驻**读循环，不能等收到 `STUN:Live` 才开始读，否则首个回包必丢。

- **方案 A（推荐）**：进程级常驻单读循环 + 以被测 Address 为键的活跃发送窗注册表。10s 限速保证同一 Address 同时至多一个窗口，故键唯一。在 DEC-0005 闭集中明确此注册表属**第 2 项（当前发送窗）的组成部分**，不算新增表，闭集仍为五项。
- **方案 B**：列为闭集第 6 项独立表。语义更直白，代价是闭集扩张，需重新论证「不为会话建模」的边界。

落点：**DEC-0005**（闭集归属）+ SPEC-0004 §4 新增一节。

> 用户裁决：同意方案 A。虽然原打算用 Key32 作为键，但用回包源地址更短小（依发包目标地址建映射即可）。

### R5 粗测起始间隔的上界（阻塞）

构想写明起始间隔 `≥10s, ≤40m`，但 `SPEC-0004` §3 只有「`< 10s` 为配置错误」，`SPEC-0001` §10 只有「≥ 10s」，上界在向下传递时丢失。

后果是连锁的：`Start = 60min` 时 `Distance = 3600+余量` 被钳到 2700，**首次**请求前批条即过期；同时 `lastFail = 60min` 使 `CanFine` 恒假（要求 `LastFail ≤ 40 分钟`），精测永不可达。一个配置错误表现成三种互不相关的运行时故障。

此项**无需取舍**（构想已明确），列在此处仅因它与 R2 共用 40/45 分钟耦合，须一并处理。裁决只需确认：上界写成硬校验，在 `NewLive` 构造期拒绝。

落点：SPEC-0004 §3、SPEC-0001 §10（Spec 补齐，随 R2 一起改）。

> 用户裁决：查看 R2 的裁决，合并处理。

### R6 Equi-X 与 cgo 的落点

`SPEC-0001` §11 把 `SolvePuzzle` / `VerifyPuzzle` 放进根包 `stun2`，§8 要求 `CGO_ENABLED=1`。但 Equi-X 只有 Cone 挑战路径用得到。于是只用 `STUN:Addr` 或 `STUN:Live` 的调用方——完全不碰 Equi-X——也被迫开启 cgo、失去纯 Go 交叉编译，并承担 equix 的 LGPL 链接与源码随附义务。项目自身是 MIT。

- **方案 A（推荐）**：Equi-X 封装下移到独立子包（如 `stun2/pow`），由 `stun2/client`、`stun2/server` 的 Cone 路径导入；根包只保留 `EquixSeed` 的 SHA-256 拼接（纯 Go）。DEC-0001 的三包表增一格或标注例外。
- **方案 B**：维持根包，在 README 与 SPEC-0001 显式声明「本库使用者一律需要 cgo，并承担 LGPL 义务」。

推荐 A 的理由：DEC-0001 划分包边界的判据是「纯函数 / IO / 角色」，而 cgo 与许可证是**分发属性**，它天然要求更细的切分；且 Live 与 Addr 两个服务在协议上与 Equi-X 完全无关。

落点：**DEC-0001**（包边界）+ SPEC-0001 §8/§11。

> 用户裁决：同意方案 A。
> 不过实际上 `github.com/cxio/equix-cgo/puzz` 本身已是 MIT 许可，它的上级根包好像已经完成了纯 Go 封装。

### R7 Challenge 绑定的源服务器材料

`SPEC-0001` §7 的 Challenge HMAC 覆盖 `ServAddr18`（含端口），`SPEC-0003` §4.5 用「当前 QUIC 对端」验证。只要受托池连接在签发与 NewHost 之间重建过（换了源端口），所有在途 Challenge 即全部失效。构想本身承认「源服务器联系受托节点不一定每次都成功」，说明重连是常态；而失败原因对客户端不可见（只见 `VerifyFailed` 或收不到包 → 被判 P-RC），排查困难。

- **方案 A（推荐）**：改绑源服务器的稳定身份（节点 ID 或 SPKI 指纹）。受托池连接由应用建立，而 p2p 节点信息中已含 `Hash256(Cert.SPKI)`，材料应当现成——需确认该材料可否注入受托侧。
- **方案 B**：只绑 IP，去掉端口。改动最小，但多 IP 出口的源服务器仍会失效。
- **方案 C**：保留 IP:Port，在 SPEC-0003 写明「受托池连接在挑战 TTL 内不得重建，否则须主动丢弃相关在途委托」，把约束推给应用提供的连接池。

落点：**新决策或 DEC-0005 修订** + SPEC-0001 §7、SPEC-0003 §4.5。若选 A，需同时确认节点身份材料由应用注入的接口形态。

> 用户决策：同意方案 A。采用 SPKI 指纹（`SPKIF`）。
> STUN2 服务网络最终需要接入 `github.com/cxio/p2p` 定义的基网里，`SPKIF` 是节点表达长期信用的字段。

### R8 受托侧对委托方的信任边界

Challenge 按构想**没有目标绑定**，故 2 分钟 TTL 内一份 Challenge 可复用于任意多个 Target；`STUN:Cone.Challenge` 请求本身既不限速也不要工作量。DEC-0005 又把受托状态钉成闭集（仅 Target 去重表），实现方不能加「按源服务器」的令牌桶。

现有唯一防线是 PoW 成本，但恶意源服务器可自行计算：p=0.1 约数百毫秒，单核约 10 个目标/秒 × 3 包，从受托 IP 发出。量级不大，问题在于**文档从未对这条路径表态**，实现者遇到时无所依据。

- **方案 A（推荐）**：在 DEC-0005 明确写出信任边界——受托池成员即受信节点，滥用由应用层剔除成员解决，故受托侧不加速率表，闭集不变。
- **方案 B**：把「按委托方的速率表」加进闭集，受托对每个源服务器设令牌桶。

推荐 A 的理由：受托池由应用提供并维护成员关系（DEC-0001 第 6 条），信任边界本就落在应用层；在库内加表会与「受托只做验证即发包」的轻状态定位冲突。但**必须写出来**，不能留空。

落点：**DEC-0005**（理由与边界补写，闭集可能不变）。

> 用户裁决：原则上同意方案 A，但此处的表述好像有问题。
> 受托放大的攻击方为源服务器，受托池也为源服务器管理。因此应用层的解决实际上落在受托方，剔除/拉黑的滥用节点实际上是源服务器，而不是受托池成员。

### R9 收集窗在受托池穷尽时的提前返回

`SPEC-0003` §4.2 情形 3 为「`Pick` 返回空且无在途 → 不再抽选，等待截止」，情形 5 禁止「满 2 未满 3 时提前返回」。结果：2 节点部署的每次 Inquire 必然烧掉客户端 11s 预算中的 7s。

但情形 3 恰是 DEC-0003 所担心情形的**反面**：DEC-0003 怕「还没抽到第 3 个就返回」，而情形 3 已证明池确已穷尽，此时提前返回是安全的。

- **方案 A（推荐）**：情形 3 改为「已收集 ≥2、池穷尽且无在途 → 立即返回」，DEC-0003 第 4 条加此例外。
- **方案 B**：维持现状，接受 2 节点部署的固定 7s 开销。

落点：**DEC-0003**（第 4 条例外）+ SPEC-0003 §4.2。

> 用户裁决：同意方案 A。
> 已修订 @conelevel.md:164 添加了：如果连接池数量不足，已遍历完全部节点，则与超时处理逻辑类似——凑齐2台即为有效，且无需等待到超时才返回。

### R10 首次 `Time.0` 的保守偏置

`SPEC-0004` §2.3 要求 `CloseWithError` 后等 `max(3*PTO, 1s)` 再记 `Time.0`。但真实的最后一次出站就是 `CONNECTION_CLOSE` 本身——按 `MEMORY.md` 第 2 条重传为收包触发，而服务端回一个 CC 后即停写，实际几乎零重传。于是测得值比真实静默期短了整个等待时长：RTT 500ms 时 PTO 约 1s，低估达 3s，已接近默认 5s 精度。

方向是保守的（宁短勿长），对保活用途安全，但这是一项**未被文档承认**的偏置。

- **方案 A（推荐）**：`Time.0` 记为 CC 实际发出时刻，在等待窗内监测是否真的发生重传，有则把 `Time.0` 顺延到最后一次重传。等待本身保留。
- **方案 B**：维持现状，在 DEC-0004 与精测精度的语义说明里把它写成已知保守偏置，并给出量级（`max(3*PTO, 1s)`）。

落点：**DEC-0004**（第 3 条）+ SPEC-0004 §2.3。

> 用户裁决：原则同意方案 A。
> 但起点 `Time.0` 记为 CC 实际发出时刻 `+1s`。如果等待窗口内收到重传，则记为真实时刻。

### R11 错误码的覆盖面

DEC-0002 第 4 条要求「拒绝必须可区分原因」，但现有 7 个码缺三项语义：**受托拒绝协助**（构想的「若愿意提供协助」意味着受托可拒，而 `InsufficientTrustees` 描述的是源服务器的收集结果，语义不同）、**通用不可用 / 内部错误**、**证明过期**（见 R3）。Status 为 u8，编号空间充裕。

- **方案 A（推荐）**：补 `ErrDeclined`（受托拒绝）、`ErrUnavailable`（暂时不可用 / 内部错误）、`ErrExpired`（证明过期）三项。
- **方案 B**：只补 `ErrExpired`（R3 必需），受托拒绝复用 `ErrUnavailable` 或直接关流。

落点：**DEC-0002**（覆盖面）+ SPEC-0001 §3（数值）。与 R3 一并裁决。

> 用户裁决：同意方案 A。

### R12 Inquire 限速的可配置性与服务能力发现

两项相关，合并一条。

**限速**：DEC-0007 已承认「CGNAT 共享 IPv4 时共享同一个 30s 占用窗」，但未评估后果——一次合法 Cone 探测就占满一个窗，同一出口 IPv4 后的所有客户端在单台源服务器上排成 1 次/30s。大型 CGNAT 下 Inquire 基本不可用，而 30s 定为不可配置，部署方无法放宽。

- **方案 A（推荐）**：改为「默认 30s、部署可上调，不可下调」，保留抗滥用下界。
- **方案 B**：改成小容量令牌桶（如 60s 内 2 个令牌），`RateLimited` 语义不变。
- **方案 C**：维持不可配置，在 DEC-0007 写明 CGNAT 场景下建议客户端换源服务器（现状即此，但未写成指引）。

**能力发现**：客户端只能靠 `UnknownMethod` 试错得知某节点是否提供 Cone / Live，而试 Inquire 的代价正是一个 30s 限速窗。DEC-0001 把节点发现划给 p2p 项目，这没问题，但「节点信息须携带服务能力位」这个**对上游的要求**未在边界描述中写出，两个项目之间留下缝隙。

> 用户裁决：同意方案 A。但默认时间收窄为 `5s`，可配置。

- **方案 A（推荐）**：在 DEC-0001 的边界里写成对上游 p2p 项目的显式要求，本库不新增方法。
- **方案 B**：新增零成本的 `STUN:Caps` 方法，本库自足。

落点：**DEC-0007**（限速）+ **DEC-0001**（能力发现边界）。

> 用户裁决：同意方案 A。
> 但实际上基于 cxio/p2p 基网的架构，STUN2 服务就是一个专用子网。节点信息携带服务标识（名识）是必须的。

### R13 闭集遗漏了 Cone 发送窗的 per-request 密钥

DEC-0005 声明「服务端允许的短暂存储是闭集，只含下列五项」，其中第 2 项专门为 Live 的发送窗 `Key32` 开了口子。但 Cone 侧同构的三处**都不在这五项里**：

- 源服务器处理 `STUN:Cone.Passage`：须持有 `Key32` 约 600ms（2 个包，间隔 100–300ms）；
- 源服务器处理 `STUN:Cone` 的 NewPort：须持有 `Key32` 最长约 1.6s（4 个包，间隔 100–400ms）；
- 受托处理 `STUN:Cone.NewHost`：须持有 `KeyHash` 最长约 1.5s（3 个包，间隔 100–500ms）。

而 DEC-0005 对受托的措辞尤其绝对：「受托侧除上述去重表外无其它状态：验证 Challenge 与 Equi-X 后即时发包」——但「即时发包」与构想规定的 100–500ms 随机间隔发 3 个包互相矛盾，实现必须在发送窗内保留 `KeyHash`。

这不是新增能力，只是措辞遗漏；但 DEC-0005 被 SPEC-0003 §4.3 / §4.6 当作规范引用，而按权威顺序 Decision 高于 Spec，严格读下来现行 SPEC-0003 §4.5 是违反 DEC-0005 的。

- **方案 A（推荐）**：把闭集第 2 项从「Live 的发送窗 Key32」推广为「**任一服务的当前发送窗密钥**（Live 的 `Key32`、Cone Passage / NewPort 的 `Key32`、受托 NewHost 的 `KeyHash`）」，统一约束为「随请求处理协程存活、发送窗结束即释放、不跨请求复用、不进入进程级会话表」；受托那句「即时发包」改为「验证通过后在发送窗内即时构造并发出，窗结束即释放」。闭集仍为五项。
- **方案 B**：逐条列举，闭集扩为七项。更直白，但会稀释「闭集」的约束力。

与 R4 相关：R4 若选方案 A（Live 的发送窗注册表归入第 2 项），本项的推广口径需与之一致，两项应一并裁决。

落点：**DEC-0005**（第 2 项措辞与受托状态描述）。

> 用户裁决：同意方案 A。
> 这确实是一个措辞容易歧义的地方，按理随处理协程同生命期是理所当然（本就没有更多负担）。

## 理由 （Rationale）

按维护总则，Spec 与上层不一致时须先改上层再重新生成下游。上列各项都触及构想语义（R2、R5）、包边界（R6、R12 后半）、闭集与信任边界（R4、R8、R13）、既有决策的例外（R9、R10）或信封与错误面（R1、R11），以及一项绑定材料选择（R7），因此都不能在 Spec 层自行决定。唯一的例外是 R3 的方案 A，它本身是 Spec 补齐，列入本单只因方案 B 与 R11 绑定。

先汇总成单再分发，是因为其中 7 项互相牵连：R2 的批条窗口与 R5 的间隔上界共用 40/45 分钟耦合；R3 的方案 B 与 R11 共用错误码面；R6 的包边界与 R12 的上游边界同属 DEC-0001；R4 与 R13 共用闭集第 2 项的口径。分散裁决会产生新的层间不一致，而这正是维护总则要防的事。

### 按收录判据被排除的项

评审中提出、经复核后**不构成问题**、任何一层都不必记录的，列此备查，以免日后重复提出：

- **`STUN:Cone.Passage` 的「请求小、响应大」不是放大攻击面。** 放大攻击的成立条件是**源地址可伪造**，不是收发比。DNS 约 70 倍即危险，而 HTTP 常达数千倍却无害，差别只在有无地址验证。Passage 必须在完成 QUIC 握手之后才能发出，握手本身即地址验证，攻击者无法让服务器把数据打向第三方；被消耗的只是服务器自己的上行，与任何对外服务无异。已认证客户端的资源消耗属接入层配额问题，DEC-0001 已划给应用（首包工作量认证）。
- 仅存的差别是：Passage 响应走裸 UDP，不受 QUIC 拥塞控制与流控约束。但构想规定的 100–300ms 随机间隔本身就是逐请求的发送节流，无需额外机制；如需提示，作为 SPEC-0003 的一句实现注记即可，不占决策。

同理，下列内容一律不进文档：并发与锁的写法、数据结构选型、日志与指标、错误包装层次、超时的具体计时器实现。判据仍是「是否改变对外可观测的行为或输出值」。

> **反证：** 本单附录第 2 行的「精测伪代码两个不可达分支」正说明规格下沉到伪代码会引入规格自身的 bug——代码里不会出现的分支，写成散文反而出现了。规格应当规定**输入到输出的映射**与**线上可见的行为**，而不是复述实现。
